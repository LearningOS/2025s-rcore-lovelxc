# 总结

实现要求中的死锁检测算法。

在每次请求资源时 (`mutex_lock` 和 `semaphore_down`)，增加 need 矩阵，然后进行死锁检测，检测完毕后如果失败，则复原 need 矩阵并返回 dead。获取到资源后，减少 work 和 need 矩阵，并增加 allocation 矩阵。

释放资源时 (`mutex_unlock` 和 `semaphore_up`) 则增加 work 矩阵，减少 allocation 矩阵的值。

当线程退出 (`exit_current_and_run_next`) 时，将 allocation 矩阵的值加回到 work，并清空 need 和 allocation 矩阵。

# 问答题

## 第 1 题

根据 `exit_current_and_run_next` 函数，当主线程 (即 0 号线程) 退出时，回收的资源有：

1. 线程资源 (TID、用户栈、Trap 上下文)
2. 进程用户内存空间，调用 `process_inner.memory_set.recycle_data_pages` 释放进程的整个用户地址空间
3. 文件描述符，通过 `process_inner.fd_table.clear` 关闭所有打开的文件描述符
4. 通过 `remove_from_pid2process(pid)` 将进程从 PID 映射表中移除，释放 PID。
5. 调用 `remove_inactive_task` 将线程从调度队列或等待队列中移除。
6. 通过 `process_inner.tasks.clear` 清除所有线程的引用，当线程的 Arc 引用计数归零时，其相关资源回被自动回收。
7. 子进程移交，所有子进程被转移到 init 进程 (INITPROC) 下，避免成为孤儿进程。同时将自身设置为僵尸进程。

## 第 2 题

Mutex1 是正确的 mutex 锁的设计，用的是标准的 "阻塞 - 队列 + 循环检查" 实现，通过状态管理和唤醒机制避免竞态与死锁。
Mutex2 是错误的实现，在 lock 中，仅检查一次锁状态，线程被唤醒时，锁可能已被其他线程抢占，导致多个线程同时进入临界区。
在 unlock 中，若最后一个线程退出临界区时队列非空，锁仍为 locked=true，但后续无线程实际持有锁，导致所有新线程永久阻塞。
